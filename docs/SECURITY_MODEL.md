# Security Model

`solana-keychain` validates the signing hop, never what a transaction does. Backends come in three shapes, and the difference matters before you put one on a path that moves value. Which shape a given backend has is in the signer-capabilities table of your language's README: [Rust](../rust/README.md#signer-capabilities), [TypeScript](../typescript/README.md#signer-capabilities), [Python](../python/README.md#signer-capabilities), [Go](../go/README.md#signer-capabilities).

**Signing backends sign the bytes you built.** The signature the provider returns is verified against your locally computed message before it is used, so you end up with a transaction you can still inspect and broadcast yourself. See the memory or Vault example in the quick-start.

**Rewriting backends sign bytes they built from yours.** One backend rewrites your bytes before signing them: Fordefi native manual mode. It may replace the recent blockhash and manage the Compute Budget fee instructions, then signs and hands the transaction back without broadcasting. What it changed is not diffed and not validated: the signature is verified against the message it returned, and the transaction you passed in is replaced with that one. The result is still something you can inspect and broadcast, but it is not the object you built, so continue from what the signer returned.

**Sending backends sign bytes you never see.** The provider builds, rewrites (to sponsor gas) and broadcasts server-side, so the returned signature identifies the transaction that landed rather than covering the bytes you submitted. It is verified against the provider's own returned bytes, which proves it identifies a real transaction but says nothing about whether that transaction is the one you asked for. A failure may still have landed on chain, so reconcile before retrying; when a batch fails, the error reports how many of its transactions had already landed. See Crossmint in the capabilities table and the sign-and-send section.

**Hardware backends move the trust boundary onto the device screen.** Ledger is a signing backend by the shape above — it signs the bytes you built, and the signature is verified against them before it is attached — but what it guarantees rests somewhere different from the others. With a remote backend the provider is trusted to sign what it was sent. With a hardware wallet the *host is not trusted at all* for what the user sees: the private key never leaves the device, and the only description of the transaction the user can rely on is the one rendered on the device's own screen, by the device's own firmware. Anything this library prints, and anything the calling application shows, is advisory. That is the point of the hardware, and it means a compromised host can misrepresent a transaction in its own UI but cannot make the device display or sign something the user did not approve.

Two consequences follow for anything built on this backend. The PIN and the on-device approval are hardware invariants that no host-side access can bypass, so host access to the device node is not equivalent to spend authority — but it is enough to enumerate the device, read public keys, and put approval prompts on the screen that the user did not initiate, which is why the Linux udev rules this backend documents grant the device to the active seat rather than to every local account. And the device is a single serialized resource: one operation at a time, one confirmation at a time, so a second signing request while a prompt is open is refused rather than queued.

**Off-chain message signing deviates from the raw-bytes contract, by necessity.** A Ledger cannot ed25519-sign arbitrary bytes the way the software backends do; it signs a structured off-chain message, so `sign_message` returns a signature over an *envelope* wrapping your payload, not over the payload. Verifying it means rebuilding the same envelope — and the envelope this backend builds is the one the Ledger Solana app parses, which is not what `solana-offchain-message` serializes. Anything that verifies these signatures server-side has to construct the same bytes; the layout is documented with the backend. This affects vouchers and credentials, not transaction signing, which covers exactly the bytes you supplied and verifies like any other backend's.

**The device driver is the one dependency this crate does not pin exactly.** `solana-remote-wallet` is taken as `"4"` rather than a fixed version, and it is the crate that drives the hardware, so a consumer's dependency graph decides which one is in the build. This is deliberate and it is a device-support decision: the Nano Gen5 product IDs arrived in 4.1, so pinning below that would make the current-generation device invisible, while pinning at 4.1+ would force the whole 4.x solana-* crate line on consumers still on the 3.x transaction line and make the backend unbuildable for them. The range is what lets both resolve. The cost is real and worth stating: consumers get whatever 4.x their graph selects, a 4.0.x resolution silently cannot see a Gen5, and the backend's own code is identical across the range. `just rust-which-remote-wallet` reports which version a given build resolved.

**Error detail from the device layer is logged, not returned.** Availability and transport failures from `hidapi` and `solana-remote-wallet` carry host paths, device identifiers and opaque upstream strings. Following the same rule as the remote backends, the returned `SignerError` keeps the remedy and drops the raw detail, which goes to `log::error!` only under the `unsafe-debug` feature. Do not enable `unsafe-debug` in production; it is a debugging aid, and on this backend it will put device paths in your logs.
