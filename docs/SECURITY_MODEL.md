# Security Model

`solana-keychain` validates the signing hop, never what a transaction does. Backends come in three shapes, and the difference matters before you put one on a path that moves value. Which shape a given backend has is in the signer-capabilities table of your language's README: [Rust](../rust/README.md#signer-capabilities), [TypeScript](../typescript/README.md#signer-capabilities), [Python](../python/README.md#signer-capabilities), [Go](../go/README.md#signer-capabilities).

**Signing backends sign the bytes you built.** The signature the provider returns is verified against your locally computed message before it is used, so you end up with a transaction you can still inspect and broadcast yourself. See the memory or Vault example in the quick-start. One of them submits your bytes to the provider before signing: Fireblocks in `useProgramCall` mode. Fireblocks is asked not to broadcast, but if it does anyway, or if the request's outcome never resolves, the failure reports `BROADCAST_UNCONFIRMED` with the provider transaction id, and something may have landed.

**Rewriting backends sign bytes they built from yours.** One backend rewrites your bytes before signing them: Fordefi native manual mode. It may replace the recent blockhash and manage the Compute Budget fee instructions, then signs and hands the transaction back without broadcasting. What it changed is not diffed and not validated: the signature is verified against the message it returned, and the transaction you passed in is replaced with that one. The result is still something you can inspect and broadcast, but it is not the object you built, so continue from what the signer returned.

Any rewrite voids a signature collected before it, so a rewriting backend has to run before every other signer, and the signatures that reach the caller are the returned transaction's own. Manual mode accepts a transaction that already carries signatures and drops them with the rewrite; native auto refuses one, because it broadcasts, and re-signing bytes the vault already signed would put the same transfer on chain a second time under a fresh blockhash, where the network's duplicate detection cannot catch it. To have the vault sign alongside others rather than ahead of them, use a signing backend.

**Sending backends sign bytes you never see.** The provider builds, rewrites (to sponsor gas) and broadcasts server-side, so the returned signature identifies the transaction that landed rather than covering the bytes you submitted. It is verified against the provider's own returned bytes, which proves it identifies a real transaction but says nothing about whether that transaction is the one you asked for. A failure may still have landed on chain, so reconcile before retrying; when a batch fails, the error reports how many of its transactions had already landed. See Crossmint in the capabilities table and the sign-and-send section.
